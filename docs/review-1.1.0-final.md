## 2. F-15 缺陷复盘（本轮最重要发现）

**现象**：真机门禁偶发 1 项失败——`approve` 返回 `400 {"error":"database is locked (5) (SQLITE_BUSY)"}`，
随后任务**永久停在 `applying`**（t+2s 仍是 applying，无 `error` 记录）。

**根因（两层）**：
1. **每连接语义误用**：`busy_timeout` / `journal_mode` 是 SQLite 的**连接级**属性，
   `sql.Open` 之后 `Exec` 一次只作用于连接池中的**一条**连接；其余连接 `busy_timeout=0`，
   遇到并发写立刻返回 `SQLITE_BUSY`。1.1.0-e 新增的"每次状态迁移写一条事件"把并发写窗口放大，
   使该问题从潜在变为必现。
2. **失败不收敛**：迁移到 `applying` 后写终态失败时直接上抛错误，任务停在中间态，
   校验脚本又未检查 approve 状态码 → 失败以"任务状态异常"的模糊形式暴露。

**修复**：
- `store.New`：SQLite 把 pragma 写进 **DSN**（`_pragma=busy_timeout(5000)`，文件库再加
  `_pragma=journal_mode(WAL)`），连接池每条新连接均生效；`SetMaxOpenConns(4)` 降低写竞争。
- 写路径统一走 `execCtx`：遇忙锁做有限退避重试（busy_timeout 之外的兜底）。
- `agent`：完成任务/回滚状态写入失败时**尽力标记 `failed`** 并上抛，不再停留在中间态。

**门禁固化**：
- `TestSQLiteLockSettings`：断言文件库 `busy_timeout=5000` 且 `journal_mode=wal`（内存库仅前者）。
- `TestConcurrentWritesNoBusy`：8 协程 × 15 轮并发"建任务 → 读 → 更新 → 写事件"，不得出现忙锁
  （**修复前该用例必失败**，是真实反例取证）。
- 真机门禁：`approve` 必须 200（失败打印响应体）+ 任务终态有界轮询。
